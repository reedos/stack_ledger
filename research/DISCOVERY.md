# Broad discovery within the existing research framework

Monitoring maintains accepted series. Discovery investigates what is missing. Recommendation proposes a change; a human reviews it; the maintained renderer and restricted publisher operate only on approved inputs. None of these roles grants itself the next role's authority.

## What runs

`research.py` invokes `discovery.py` inside its existing lock. The session controller repeats this runner; it supplies no credentials or tools to the model. Balanced daily/manual batches reserve 25% for private discovery. Operator presets may choose 0%, 75% or 100%; focused source/question runs skip discovery. The reservation includes searches and pages, not just successful retrievals. At most one search runs per batch, five results per search, four local-model calls and 300 seconds of discovery time, further capped at the selected fraction of the batch time. Both model passes are bounded by remaining discovery time. Existing HTTP/robots requests can finish beyond the boundary; this is not hard process preemption. Monitoring keeps its existing public receipt and publication restrictions. Fully exploratory runs write only private discovery receipts, never a public monitoring success.

Layer choices filter rotating search topics and eligible saved leads. Source-category choices add fixed search cues and an operator preference to the question; they do not establish source authority or exclude every mismatched backlog lead. Reviewed collection rank filters apply to registered monitoring sources. Neither selection changes public host/path permissions. Private session monitoring keeps cumulative proposal data and screening cache separately from accepted public data. See `RESEARCH_SESSIONS.md` for duration, control-panel and stop behavior.

The [GDELT DOC 2.0 adapter](https://blog.gdeltproject.org/gdelt-doc-2-0-api-debuts/) uses a fixed HTTPS endpoint, JSON article lists, a one-month window and no credentials. Broad queries come from reviewed configuration; bounded catalog follow-up queries use sanitized names from accepted project/product catalogs. Search results are untrusted leads, not primary evidence or statements of fact. Missing/invalid responses and access restrictions are recorded with HTTP status and Retry-After when available. Provider-wide cooldowns persist across batches and topics: at least one minute between successful searches, and failures back off from 15 minutes up to six hours, honoring a longer Retry-After. Rejected query syntax cools the topic without declaring a provider outage. Excess article results are truncated to the configured lead budget. There is no access-control bypass or paid fallback. This is a news index, not an exhaustive web search. Original filings, papers, employer feeds and statistical APIs still need additional reviewed adapters.

Questions cycle through every layer and topic before changing between delivery and constraint lenses and then regions. Named companies are not required search terms. This supports emerging builders and occupations without a model silently rewriting the research mandate. Regional keyword searches do not establish local-language completeness. A one-month search window concerns discovery recency only; source forecasts beyond 2030 remain eligible.

## New hosts and retained leads

The runner imports eligible URLs from the existing `.local/discovery-leads` archive with known registry ancestry. Search results and up to three eligible one-hop links per fetched document can seed additional private investigations. Registered primary index pages seed private leads in the selected layers on every slice, independent of search-provider health; they undergo the same robots, host, format, evidence and review controls. This can investigate existing primary sites but is not a replacement general web-search engine. New hosts must use HTTPS, no credentials/query strings/literal IP addresses, public DNS, supported readable content and robots permission. Login, account and application paths remain excluded; eligible RSS/Atom, JSON and CSV/TSV documents can be collected through the bounded text adapters. The existing same-host redirect rule remains: foreign redirects are skipped rather than automatically trusted. PDFs, Excel workbooks and dynamic-only content remain explicit collection gaps. Unsupported document pointers are retained in private discovery state, and fetched format/insufficient-text gaps are recorded under `.local/collection-gaps/`. They do not enter the model as empty evidence. Model output never supplies network requests, paths, shell commands or configuration.

The private lead store deduplicates canonical URLs, rotates fresh and backlog priority, retains provenance and hashes, and records the last attempt and next eligible attempt. Unchanged documents skip inference when model, code, agenda, coverage and policy are unchanged. Normal revisits take seven days; failures back off from one day to a maximum of 30. Failed screening is not cached as successful research. Human-prioritized investigation is ordered first when eligible. At 2,000 leads the store flags capacity reached; reviewing/archiving that backlog requires maintenance rather than silent eviction or unbounded crawling. Unsupported pointers remain in their original archive.

Since September 10, 2026, discovery shares `Fetcher` (and its private per-URL `.local/fetch-state.json`) with monitoring: see OPERATING_GUIDE.md's "Review ledger, conditional fetches and adaptive cadence." A revisited lead whose fetch confirms an HTTP 304 is recorded `unchanged` (not a failure, not a backoff), same as any other unchanged monitoring page; this only ever fires for a lead URL that already has stored validators from an earlier fetch.

## Evidence and review

Each new model proposal identifies its actual layer (within operator-selected layers), a company, project, source, metric, occupation or topic; an attributed claim; actual/estimate/forecast/commitment/unknown basis; exact evidence; why it may deserve tracking; and a next question. The latter two are proposals, not proved benefits. The extraction prompt includes current layer company names, metric IDs and the active agenda. Numeric token checks and a second skeptical model pass screen the claim. Publisher authority and novelty remain unverified until human review. Empty findings and rejected screening are valid outcomes. Empty results now require a diagnostic reason. Company names and metric IDs do not establish that a specific claim is already covered. Attributed future company plans belong under commitment; lack of independent corroboration does not by itself make an accurately attributed commitment unusable for private follow-up. It still cannot establish delivery.

Proposals extend `.local/review-candidates` as `discovery-*.json` with `kind: coverage_expansion`. They use the same editorial event log and lock. Discovery never appends to the public ledger, creates catalog IDs, registers a source or changes homepage recommendations. Evidence bodies are private. The digest renders untrusted prose as indented text; it is never included in generated site assets.

Human triage is available in the local Research Control panel's **Review findings** tab (source/evidence cards, reason and explicit confirmation), or through the existing interactive local-account check below. Both use the same queue, reviewer mapping and append-only audit log. The panel also checks evidence and prior-decision hashes before saving; neither route approves publication.

```powershell
python scripts/editorial_review.py review-discovery discovery-<id> --decision investigate --reviewer reedos --rationale "Verify the original permit and proposed measurement scope"
```

The human types the complete ID. `investigate`, `deferred` and `rejected` are triage decisions; none means approved publication. Priority is applied to later eligible lead checks; this does not run an autonomous custom-question agent. Implementing a new source, company, project or metric remains a separately reviewed repository change with original-source checks, catalog/source updates and normal tests. Homepage selection still goes through its separate incumbent-versus-challenger review on frozen accepted data. Discovery cannot invoke review commands or approve itself.

## Monitoring progress safely

```powershell
python scripts/discovery.py
python scripts/discovery.py --documents 8
python scripts/discovery.py --status
Get-Content .local/discovery/digest.md
```

The first two commands only preview; they do not start inference, search, import or modify state. Status falls back to the plan before the first run. During execution `.local/discovery/latest.json` identifies the topic, attempted pages, counts and errors; the digest is written at the end of each slice. Historical receipts are in `.local/discovery/runs/`. Page/source retrieval, successful screening, queueing, human triage, acceptance and publication are different events. Public hardware attribution and runtime presentation are unchanged.

Assess usefulness by evidence-backed proposals and eventual reviewed additions, with layers, unknowns and rejected/empty results visible. The current digest counts proposals and human triage separately; it does not automatically certify novelty, causal effects or catalog adoption. Fetch counts alone cannot establish expanded coverage. Inspect the actual reviewed catalog diff before reporting an adopted addition.

## Text exposure, evaluation and question progress

`evidence_text.py` selects the opening, tail and question-relevant contiguous sections inside the existing 18,000-character discovery or 24,000-character monitoring budget. Both extraction and screening receive the same sections. An evidence quote must fit inside one contiguous exposed range; it cannot bridge omitted text. Numeric matching accepts sentence-ending periods while rejecting partial decimals, identifiers and implicit scaling. Section metadata and helper implementation hashes invalidate stale model-screen caches when processing changes.

Private `.local/discovery/screens/` retains empty-result reasons and rejected candidates with screening verdicts. Exposure ranges describe text supplied to a model, never proof of comprehension. A partial empty screen is not an exhaustive negative finding; the remaining text requires later targeted review. Historical receipts without exposure metadata remain unknown. The discovery digest groups activity and linked proposals by the actual research question, with missing/partial exposure visible. Session completion additionally writes `research-progress.json` and `research-progress.md`, reusing the existing editorial question queue and human result log. No model resolves a question.

`python scripts/evaluate_collection.py --session <32-character-session-id>` audits retained documents and quarantines without network, inference, approval or publication. The maintained `collection-audit-cases.json` contains purposive evaluation labels, not approved facts. `python scripts/evaluate_discovery_model.py` previews a two-case replay; `--run` explicitly uses local Ollama, the existing exclusive locks, at most four model calls and 240 seconds. It reads saved evidence only and never enqueues or publishes its results. A two-case result cannot establish a recall rate or overnight reliability.

RSS/Atom declarations and document links are pointers, not network instructions. Every child still passes the canonical URL, public-DNS, same-host redirect, robots, byte-size, time and private-review restrictions. XML declarations/entities are rejected. CSV/TSV and JSON preserve source tokens without formula or code execution; tables still need semantic scope/unit review. No PDF/OCR/Excel parser, JavaScript browser execution, query-bearing source endpoint, second general search provider or public-source permission was added. These remain explicit adapter work, not reasons to retry an unsupported page all night.
## Catalog handoff

Screened findings may also draft a private catalog change package within the existing discovery model/time budget. The existing review queue retains insufficient-evidence and malformed-draft outcomes. Follow [CATALOG_FEEDBACK_LOOP.md](CATALOG_FEEDBACK_LOOP.md) for preview, separate human approval, application and live-data verification. Private IDs and exact URLs in a draft are proposals only; public registration and publication permissions are unchanged.

Use the decision routine embedded in [OPERATING_GUIDE.md](OPERATING_GUIDE.md) during extraction and screening. [MUSE_RESEARCH_PLAYBOOK.md](MUSE_RESEARCH_PLAYBOOK.md) specifies worked examples, follow-up wording, review-reason conventions and a larger calibration design. The existing saved-evidence replay remains two cases; the broader design is not implemented or certified by this documentation.

The broad topic sequence now occupies three out of four discovery searches; the fourth rotates through accepted project/product questions using sanitized catalog names. Both use the same provider, scope, work budgets and cooldowns. The runner does not accept arbitrary model-generated search queries. A suggested revisit trigger inside a question does not create a scheduled task.
